한동안 Synology와 QNAP 제품을 대상으로 NAS 취약점 분석을 진행해왔습니다. 그러던 중 문득 PlayStation도 한번 분석해보고 싶다는 생각이 들었습니다.

처음에는 펌웨어를 얻고 파일 시스템을 열면 다음 단계가 보일 줄 알았습니다. 그런데… PS4에서는 플래시에서 읽어온 데이터, 저장된 실행 파일, 실제로 동작하는 코드가 생각보다 쉽게 연결되지 않았습니다.

보드를 분해해 덤프를 얻는 데서 시작했고, 이후 raw13g 코드와 GoldHEN 환경을 살펴보며 실행 중인 커널의 코드 영역까지 확보했습니다. 이번 글에서는 그 사이에 무엇을 확인했고, 어디에서 다시 막혔는지 정리해보겠습니다.

> **함께 읽는 글**
>
> JavaScript 파일 구조와 주요 함수는 [[PS4] raw13g 코드 분석](/ko/posts/ps4-raw13g-review/)에 따로 정리했습니다. 이 글은 그 분석을 시작하기 전의 장비 조사와, 이후 실장비에서 확인한 내용을 이어 쓴 기록입니다.

## 1. 일단 장비부터 살펴봤습니다

장비를 받자마자 전원을 켜고 시스템 버전을 확인했습니다. 처음 확인한 버전은 **13.50**이었고, 이후 **13.52** 상태에서도 조사를 이어갔습니다.

![연구 대상으로 준비한 흰색 PS4 Pro와 컨트롤러](/assets/research/ps4-pro-research-journey/01-console.webp)

*연구 대상으로 준비한 PS4 Pro. 장비를 다시 살 여유는 없기 때문에 조심해서 진행해보겠습니다.*

NAS를 볼 때는 펌웨어 파일을 구하거나 관리 기능과 SSH를 통해 내부를 살펴보는 경우가 있었습니다. PS4에서는 제가 익숙했던 출발점을 바로 찾기 어려웠습니다. 우선 하드웨어에서 직접 확인할 수 있는 것부터 보기로 했습니다.

다행히 PlayStation 공식 채널에 [PS4 Pro 분해 영상](https://www.youtube.com/watch?v=euBlNq5kda0)이 올라와 있었습니다. 나사와 커넥터 위치를 참고하면서 메인보드가 보이는 상태까지 분해했습니다.

![커버를 분리하고 메인보드를 확인한 PS4 Pro](/assets/research/ps4-pro-research-journey/02-open-board.webp)

보드에 인쇄된 표기는 **NVG-004**였습니다. 같은 PS4라도 보드 리비전이 다를 수 있으니, 인터넷에서 찾은 사진과 제 장비가 같은 구조인지부터 대조했습니다.

![메인보드에 인쇄된 NVG-004 표기](/assets/research/ps4-pro-research-journey/03-board-revision.webp)

![조사 당시 참고한 PS4 보드 리비전별 서비스 헤더 비교 자료](/assets/research/ps4-pro-research-journey/04-board-reference.webp)

*조사 당시 참고한 [ps4-wee-tools의 보드 비교 자료](https://github.com/andy-man/ps4-wee-tools). 제 보드는 우측의 NVG 계열 그림과 대조했습니다.*

UART 포인트도 눈에 들어왔습니다. 다만 위치를 찾았다고 바로 부팅 로그나 셸을 얻는 것은 아니었습니다. 이 단계에서는 보드의 통신 포인트를 살펴봤고, UART 셸을 확보한 결과로 기록하지는 않았습니다.

## 2. 익숙한 Winbond 칩이 보이네요

![보드 위 Winbond W25Q256JV 플래시 메모리 확대 사진](/assets/research/ps4-pro-research-journey/05-flash-chip.webp)

플래시 메모리의 표기를 확인해보니 **Winbond W25Q256JV**였습니다. [공식 데이터시트](https://www.winbond.com/hq/support/documentation/?__locale=en&category=%2F.categories%2Fresources%2Fdatasheet%2F&family=%2Fproduct%2Fcode-storage-flash%2Fqspi-nor%2Findex.html&line=%2Fproduct%2Fcode-storage-flash%2Findex.html&pno=W25Q256JV)에서 패키지와 핀 기능을 먼저 확인했습니다.

W25Q256JV는 256Mbit 용량의 SPI NOR 플래시입니다. 바이트로 환산하면 **32MiB**이며, 이는 해당 칩의 용량입니다. PS4 전체 저장장치나 펌웨어 전체의 크기와는 구분해야 합니다.

![W25Q256JV 데이터시트의 패키지와 핀 기능 표](/assets/research/ps4-pro-research-journey/06-datasheet.webp)

또 스크립트를 작성해야 하나 걱정했는데, 찾아보니 flashrom에도 이 계열을 다루는 정의가 있었습니다!

![flashrom의 Winbond 플래시 지원 정의를 확인한 화면](/assets/research/ps4-pro-research-journey/07-flashrom.webp)

*당시 확인한 [flashrom의 Winbond 칩 정의](https://github.com/flashrom/flashrom/blob/main/flashchips/winbond.c). 칩 이름뿐 아니라 용량과 지원 동작도 함께 살펴봤습니다.*

데이터시트로 실제 칩의 규격을 확인하고, flashrom 소스에서 도구가 그 칩을 어떻게 식별하는지 대조했습니다. 읽기 작업에는 **Raspberry Pi와 PCBite**를 사용했습니다.

![PCBite 프로브를 연결해 PS4 Pro의 플래시 데이터를 읽던 작업 모습](/assets/research/ps4-pro-research-journey/08-dump-setup.webp)

회사 사수와 함께 추출을 진행했고, 다행히 덤프 자체는 확보할 수 있었습니다.

## 3. 덤프를 얻는 것과 내용을 이해하는 것은 달랐습니다

여기까지 오면 조금은 쉽게 풀릴 줄 알았습니다. 그런데 `binwalk`로 살펴봐도 기대했던 파일 시스템이나 알아보기 쉬운 시그니처가 바로 잡히지 않았습니다.

처음에는 “혹시 RTOS라서 그런가?” 하는 생각도 했습니다. 암호화된 데이터인 건가 싶기도 했고요. 다만 **시그니처가 잡히지 않았다는 결과만으로 운영체제 종류나 암호화 여부를 확정할 수는 없습니다.** 어떤 영역을 읽었고, 그 안에서 어떤 형식을 기대하는지부터 알아야 했습니다.

당시 결과를 정리하면 다음과 같습니다.

| 항목 | 확인한 내용 |
|---|---|
| 장비 | PS4 Pro, NVG-004 |
| 시스템 버전 | 13.50, 이후 13.52에서도 조사 |
| 조사한 칩 | Winbond W25Q256JV, 32MiB SPI NOR |
| 확보한 자료 | 플래시에서 읽어온 원시 데이터 |
| 초기 분석 결과 | `binwalk`로 기대한 파일 시스템·시그니처를 바로 식별하지 못함 |

파일 하나가 생겼다고 곧바로 실행 파일이나 파일 시스템을 분석할 준비가 끝난 것은 아니었습니다. **데이터를 읽는 작업 다음에는 그 데이터가 무엇인지 식별하는 작업이 남아 있었습니다.**

쉽게 갈 수 있을 줄 알았는데, 여기서부터 일이 조금 복잡해지기 시작합니다…ㅠㅠ

## 4. raw13g 분석과 GoldHEN 이후의 관찰

저장된 데이터만으로 내부 동작을 이해하기 어려워, 이후에는 실행 중인 장비도 함께 살펴봤습니다. 공개된 `raw13g` 코드를 분석했고, 제 장비에서 **GoldHEN이 표시되는 것까지 확인했습니다.**

화면에서 결과를 확인하고 나니 이번에는 코드가 궁금해졌습니다. 여러 JavaScript 파일이 어디에서 연결되는지, Worker는 무슨 일을 하는지, 외부 바이너리는 어떤 흐름으로 불러오는지 알고 싶었습니다.

이 내용은 [[PS4] raw13g 코드 분석](/ko/posts/ps4-raw13g-review/)에 따로 정리했습니다. 여기서는 그 이후 장비에서 관찰한 내용으로 이어가겠습니다.

처음에는 GoldHEN이 표시되면 일반적인 리눅스 장비처럼 셸에 붙을 수 있는지 궁금했습니다. 그런데 [GoldHEN의 기능 설명](https://github.com/GoldHEN/GoldHEN/blob/master/README.md)을 읽고 실제 동작을 살펴보니, 각 서비스는 역할이 달랐습니다.

| 서비스 | 문서에 안내된 포트 | 연구에서 구분한 역할 |
|---|---:|---|
| FTP Server | 2121 | 접근이 허용된 파일의 목록 확인·전송 |
| Klog Server | 3232 | 로그 출력 확인 |
| BinLoader | 9090 | 별도 프로그램을 전달받아 로딩하는 기능 |

파일을 전송하거나 로그를 받는 기능을 명령 셸과 같다고 볼 수는 없습니다. 메뉴에 기능이 있다는 것과 그 기능이 켜져 있다는 것, 실제 연결이 되는 것도 따로 확인할 항목이었습니다.

처음에는 닫혀 있던 일부 서비스가 이후 연결을 받는 상태로 바뀐 기록은 [기존 글의 포트 확인 부분](/ko/posts/ps4-raw13g-review/#section-8-포트-상태로-확인한-내용)에 정리했습니다. 이때부터는 화면에 보이는 결과와 각 서비스의 동작을 나누어 기록했습니다.

## 5. 같은 펌웨어 이야기인데 파일은 서로 달랐습니다

이후 자료를 정리하다 보니 “펌웨어 덤프”라는 표현 하나로 묶기 어려운 파일이 많아졌습니다. 업데이트 파일과 플래시 데이터, 저장된 커널 파일과 실행 중인 커널 코드는 같은 형태의 자료가 아니었습니다.

| 자료 | 이 글에서 구분한 의미 |
|---|---|
| SPI NOR 원시 덤프 | 칩에서 직접 읽은 바이트 |
| PUP | 업데이트 패키지 |
| CoreOS 슬롯 자료 | 시스템 구성요소가 들어 있는 슬롯 단위의 자료 |
| SELF | 실행 이미지와 메타데이터를 담는 Sony 컨테이너 형식 |
| 런타임 커널 text | 실행 중인 커널에서 확보한 코드 영역 |

처음에는 전부 펌웨어와 관련된 파일이니 비슷하게 열릴 거라 생각했습니다. 하지만 파일의 출처와 형식을 구분하고 나서야, 어떤 도구로 무엇을 확인해야 하는지 조금씩 정리됐습니다.

실장비에서 확보한 CoreOS 슬롯 자료에서는 내부 SELF를 분리할 수 있었습니다. **슬롯 A에서 분리한 SELF는 13.52, 슬롯 B의 SELF는 13.50을 선언**하고 있었습니다. 이 가운데 `80010002` 객체는 AMD64 커널 SELF로 식별했습니다.

| 자료 | 파일 크기 | 분석 기록에서 확인한 상태 |
|---|---:|---|
| 슬롯 A의 `kernel.self` | 10,866,322바이트 | 13.52 선언, 내부 세그먼트에 암호화 속성 유지 |
| 슬롯 B의 `kernel.self` | 10,865,570바이트 | 13.50 선언, 내부 세그먼트에 암호화 속성 유지 |

자료 사이의 관계를 그리면 다음과 같습니다. 슬롯에서 분리한 SELF와 실행 중인 커널에서 확보한 ELF를 나누어 배치했습니다.

![CoreOS 슬롯 A·B의 kernel.self와 실행 중인 13.52 커널에서 확보한 kernel_text.elf의 관계](/assets/research/ps4-pro-research-journey/09-material-structure-ko.svg)

*화살표는 자료의 포함·수집 관계를 나타냅니다. 저장된 CoreOS 자료와 런타임 코드 자료를 각각 묶었습니다. SELF의 내부 세그먼트에는 암호화 속성이 남아 있고, 런타임 ELF에는 확보한 R-X 코드 영역이 들어 있습니다.*

여기서도 한 단계가 더 남아 있었습니다. 바깥쪽 슬롯 구조를 읽고 SELF 헤더를 식별했다고 해서, 내부 실행 코드까지 바로 읽을 수 있는 것은 아니었습니다. 컨테이너를 분리한 결과와 그 안의 코드가 분석 가능한 상태인지는 따로 봐야 했습니다.

## 6. 실행 중인 커널의 코드 영역을 확보했습니다

저장된 SELF를 살펴보는 것과 별개로, 13.52 실장비에서 실행 중인 커널의 **text 영역을 확보해 `kernel_text.elf`로 보존**했습니다. 초기 플래시 덤프와 달리, 이번에는 코드 분석에 사용할 수 있는 ELF가 생겼습니다.

확보한 파일의 정보는 다음과 같습니다.

| 항목 | 확인한 값 |
|---|---|
| 파일 크기 | 13,625,176바이트 |
| ELF 형식 | ELF64, little-endian |
| 대상 아키텍처 | AMD64 / x86-64 |
| ELF OS ABI 표기 | FreeBSD |
| 로드 세그먼트 | `PT_LOAD` 1개 |
| 세그먼트 권한 플래그 | 읽기·실행 가능, 쓰기 플래그 없음 (`R-X`) |

파일을 식별하는 SHA-256도 함께 남겼습니다.

`44e2afd250f6bf60bef56dd73e3290c89cda330f2a0ccd980127e4c33ddeb67f`

여기서 `PT_LOAD`는 ELF의 프로그램 헤더가 로드할 영역을 설명한다는 뜻이고, `R-X`는 그 영역에 읽기·실행 플래그가 설정되어 있다는 뜻입니다. 확보한 파일에는 이런 세그먼트가 하나 있습니다. 이 정보를 확인하면 “커널 파일을 얻었다”는 표현을 조금 더 정확하게 쓸 수 있습니다.

이번 산출물은 **정적 분석에 사용할 커널 코드 이미지**입니다. 실행 중인 장비의 모든 메모리 상태가 들어 있는 전체 커널 덤프는 아닙니다. 커널의 쓰기 가능한 데이터 영역이나 각 프로세스의 상태까지 함께 보존한 자료로 해석하면 안 됩니다.

또한 ELF 헤더의 권한 플래그는 파일의 구성을 설명합니다. 그것만으로 수집 도구의 동작 전체가 검증되거나, 수집 당시 페이지 권한을 모두 복원할 수 있는 것은 아닙니다.

그래도 처음에 `binwalk` 결과를 보고 멈췄던 것과 비교하면 꽤 진전이 있었습니다. 이제는 IDA 같은 도구에서 코드를 읽고, 함수 간 호출 관계를 따라가며 질문을 구체화할 수 있게 됐습니다.

## 7. 업데이트 처리도 계층을 나눠서 봤습니다

PUP 파일을 살펴볼 때도 파일 형식만으로 전체 동작을 설명하기는 어려웠습니다. 업데이트를 요청하는 코드, 패키지를 읽고 검증하는 코드, 하위 처리를 담당하는 인터페이스가 나뉘어 있었기 때문입니다.

`safemode.elf`에서는 `sceUpdaterVerifySign`, `sceUpdaterReadUpkg`, `sceUpdaterUpdateUpkg`가 포함된 오류 문자열을 확인했습니다. 문자열의 참조 위치를 따라가며 각각 검증, 패키지 읽기, 업데이트 처리와 관련된 호출을 구분했습니다.

| 분석한 단서 | 확인한 내용 |
|---|---|
| 업데이트 관련 오류 문자열과 참조 | 실패 지점에서 어떤 작업을 수행하려 했는지 추적 |
| `/dev/pup_update0` 참조 | 상위 코드가 하위 업데이트 처리를 요청하는 장치 인터페이스 |
| 장치 제어 요청(`ioctl`) 주변 코드 | 헤더·세그먼트·블록 단위로 처리 요청이 나뉘는 구조 |

확인한 요청 구조를 도식으로 정리했습니다. 장치 인터페이스 아래의 세 갈래는 처리 단위별 구분이며, 요청의 반환값은 상위 코드에서 다시 확인합니다.

![PUP를 읽는 safemode.elf에서 pup_update0 인터페이스로 요청하고 헤더·세그먼트·블록별 결과를 처리하는 개념도](/assets/research/ps4-pro-research-journey/10-update-flow-ko.svg)

*정적 분석에서 확인한 요청과 결과 처리의 개념도입니다. 헤더·세그먼트·블록을 표시한 세 상자는 물리적으로 분리된 장치나 세 번의 고정된 실행 순서를 뜻하지 않습니다.*

문자열 하나를 찾았다는 것만으로 그 함수의 역할이 전부 확정되는 것은 아니었습니다. 어디에서 호출하고, 어떤 인자를 넘기며, 반환값을 어떻게 처리하는지 함께 봐야 했습니다.

이 과정에서 중요했던 것은 **정적 분석으로 확인한 호출 관계와 실제 장비에서 실행을 관찰한 경로를 구분하는 것**이었습니다. 코드에 업데이트 호출이 존재한다는 사실과, 이번 실험에서 그 경로로 업데이트를 수행했다는 주장은 서로 다릅니다. 이 부분은 파일과 호출 구조를 분석한 결과로 정리했습니다.

## 8. 관측 결과를 해석하며 다시 확인한 부분

LaunchPad와 BinLoader도 구분했습니다. LaunchPad가 저장된 프로그램을 찾는 위치와, 네트워크로 받은 파일을 BinLoader가 임시 처리하는 위치는 역할과 수명이 달랐습니다. 목록에서 파일이 보인다는 것만으로 해당 파일을 정상적으로 로딩할 수 있다고 판단할 수도 없었습니다.

파일 형식에 관한 기록 역시 점검이 필요했습니다. 일부 조사에서는 ELF 형식을 요구하는 동작을 관찰했지만, 기존 수집 기록에는 다른 형식의 전송 사례도 있었습니다. 따라서 “BinLoader는 항상 ELF만 받는다”라고 묶기보다 **사용한 버전·로더 구현·실제 파일 형식**을 함께 기록하는 편이 정확했습니다.

작은 메모리 조각을 비교할 때도 비슷한 일이 있었습니다. 256바이트씩 읽은 두 구간의 시작 위치가 `0x10`, 즉 16바이트만 다르면 **240바이트가 겹칩니다.** 이 경우 반복되는 내용은 별도 구조의 특징이 아니라 같은 메모리를 중복해서 읽은 결과일 수 있습니다.

조각 네 개를 이어 붙여 파일 크기가 1,024바이트가 되어도, 서로 떨어져 있거나 겹치는 구간이었다면 연속된 1,024바이트를 확보한 것은 아닙니다. 파일 크기뿐 아니라 각 조각의 시작 위치와 범위를 함께 남겨야 했습니다.

## 9. 이제 코드와 장비를 함께 볼 수 있게 됐습니다

처음에는 플래시에서 데이터를 읽어오면 분석이 시작될 줄 알았습니다. 실제로는 읽어온 바이트의 정체를 확인하고, 컨테이너와 실행 코드를 구분하고, 저장된 파일과 런타임 자료를 연결하는 과정이 더 필요했습니다.

이번 연구에서는 **플래시 덤프 확보 → CoreOS 내부 SELF 식별 → 13.52 런타임 커널 코드 확보**까지 이어졌습니다. raw13g 분석은 이 과정에서 소프트웨어의 진입 흐름을 이해하는 데 도움이 됐고, 후속 조사는 실제로 확보한 자료가 무엇을 보여주는지 확인하는 작업이었습니다.

다음에는 확보한 커널 text와 시스템 모듈을 함께 보면서 업데이트 처리의 호출 관계를 더 살펴보려고 합니다. 버전마다 어떤 부분이 달라지는지, 정적으로 읽은 동작이 실제 로그와 어떻게 연결되는지도 궁금합니다.

아직 살펴볼 부분은 많습니다. 그래도 막연히 “PlayStation도 한번 분석해보고 싶다”라고 생각했던 때보다는, 어떤 자료를 가지고 있고 다음에 무엇을 봐야 하는지 훨씬 분명해졌습니다.

한동안은 NAS에 빠져 있었는데, 이제는 플스도 계속 보게 될 것 같네요.
