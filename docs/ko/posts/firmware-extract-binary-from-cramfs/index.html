2025년 8월 23일·2 분 읽기

펌웨어를 분석하는 과정에서 온라인 상에서 구할 수가 없고, uart 같은 방법으로 셸 접근이 막혀 있는 상황이면은 칩에서 직접 펌웨어 추출을 시도하게 된다.

근데 이 과정에서 일반적으로는 펌웨어가 정상적으로 잘 추출 되겠지만, 진짜 드물게 제대로 추출되지 않는 상황이 발생한다.

비전공자도 이해하기 쉽게 한 가지 비유로 설명하자면,

잘 쌓여있는 단단한 하나의 블록 탑이 있다. 근데 이거를 옮기는 과정에서 중간에 위치한 블록이 빠지거나 방향이 흐트려 진 상황이다.

이 상황에서 해당 탑이 처음의 단단하던 그 탑과 완전히 같은 탑이라고 할 수 있을까??

펌웨어도 이와 같다.

펌웨어를 추출하는 과정에서 제대로 추출되지 않아 내부 데이터가 바뀐다면 그것은 더 이상 원본과 완전히 동일한 펌웨어가 아니다. 

때문에 내부 바이너리나 스크립트에서 제대로 추출이 되지 않은 부분이 존재할 것이다. 

물론 그 전에 압축해제부터가 안될 것이다. 

압축 방식에는 gzip, cramfs 등 다양한 방식이 존재한다.

그리고 각 방식에는 고유의 구조를 가지고 있는데 이게 깨지거나 변조 되면 압축 해제 정상적으로 되지 않는다.

이 상황에서 그럼 그냥 포기를 해야할까??

만약 cramfs라면 방법은 있다!!!

펌웨어 전체를 제대로 분석하진 못하더라도 내부 스크립트나 바이너리 일부 정도는 추출할 수 가 있다.

물론 gzip 같이 데이터 전체를 압축해버리는 경우는 CRC로 인한 무결성 부분을 어케 할 수가 없어 불가능에 가깝지만 cramfs면 가능하다.

cramfs 구조는 생각보다 간단하다.

[이미지 출처 : https://blog.naver.com/lovinghc/30039653478 ]

이제 설명을 위해 cramfs로 압축된 파일 시스템 하나를 준비해보겠다,

iptime a2004ml의 rfs를 cramfs로 재압축했다.

압축된 파일을 xxd 명령으로 확인해보면 바이너리, 디렉터리 등의 파일 이름들이 보인다.

이제 cramfs로 압축된 파일의 헤더에서 파일에 대한 정보와 함께 바이너리의 압축 데이터를 찾아 들어가보겠다.

위의 정의를 가지고 그림으로 표기하면 위와 같다.

파일 복호화가 복적인 상황에서는 저 부분은 다 확인할 필요가 없다.

blocks와 Files만 확인하고 넘어가도 크게 문제될 것은 없다. (BLOCKS : 0x133e, FILES : 0x02b9)

이제 INODE 부분에 대해 살펴볼 건데 여기는 압축 데이터가 어느 OFFSET에 위치하고 있는지, 그리고 그 파일이 바이너리/디렉터리 인지, 권한은 무엇인지 등에 대한 정보를 가지고 있다.

rfs에는 많은 디렉터리와 바이너리가 존재한다. 이 중 httpd 디렉터리를 살펴보겠다.

INODE 구간에서 httpd를 탐색하면 0x1068 부터 httpd의 데이터가 존재하는 것을 확인할 수 있다.

INODE의 각 정보별로 설명을 해보자면,

1. [ fd41 e803 -> 0x03e841fd ] 

  • UID : 0xe803
  • MODE : 0x41fd (0x4000 : direcotry, 권한 : 0775)

2. [ fc00 00e8 -> 0xe80000fc ]

  • SIZE : 0xfc = 252 Byte
  • GID : 0xe8

3. [ c207 0100 -> 0x000107c2 ]

  • 상위 6 비트 : namelen -> 0x2( 8 byte )
  • 하위 26비트 : data offset -> 0x107c

0x107c도 INODE 구조체 구간으로, 바이너리 정보들을 가지고 있다.

# httpd는 디렉터리이기 때문에 데이터 정보를 따로 가지고 있지 않기 때문에 내부에 존재하는 파일들에 대한 데이터를 가지고 있다.

이제 바이너리를 복호화를 원한다면 동일한 방법으로 추적하면 된다.

이제 파일 복구를 시도해볼 건데, 디렉터리나 그런 파일들이 아닌 이번엔 busybox를 복호화 해보겠다.

일반 바이너리 파일에 755 권한을 가진 busybox 파일이다.

offset은 0x13408 이다.

해당 구간으로 들어오면은 압축 데이터가 아니라 또 다른 곳을 가리키는 포인터 테이블이 존재하는 것을 볼 수 있다.

INODE의 data offset은 압축 데이터의 위치를 의미하지 않고 압축 데이트의 실제 위치를 지닌 포인터 테이블에 대한 값을 가지고 있다.

이때 하나의 포인터가 아닌 여러개의 포인터들이 존재하는 이유는 페이지 단위로 데이터를 분리해두었기 때문이다. 

플래시 메모리에 있는 펌웨어가 그대로 올라가서 동작하는 것이 아닌 페이지 단위로 쪼개서 올라가기 때문이다.

또한 cramfs에 의해 압축된 데이터는 zlib으로 압축되어 있다. 해당 압축 방법은 압축되었을 때의 최대 크기가 제한되어 있기 때문에 저 안에서도 여러개의 압축된 데이터들이 존재한다. 

자 이제 포인터들이 가보면 0x78da라는 시그니처가 존재한다.

DEFLATE 로 압축된 zlib 파일의 시작을 의미하는 곳으로 다음 zlib 시그니처가 나올때까지가 하나의 데이터 덩어리이다.

이제 이 0x14b2a offset부터 데이터 크기의 끝까지 zlib 시그니처를 탐지해보며 복호화를 시도해보면 된다.

코드 작성 귀찮으면 그냥 AI 한테 물어봐도 잘 알려주니까~ 올려두진 않겠다.
